# ColumnPicker (added 2026-08-17, revised 2026-08-17 — dropped the confirm/cancel step; grouped variant added 2026-08-25)
Dropdown panel behind the `settings` icon-only trigger already declared as the last row in `ToolbarSimple`'s and `FilterCard`'s trailing action clusters (`references/components/data/toolbarsimple.md` / `filtercard.md`, row 7 / row 4 respectively — "trailing utility action, column/display config"). Source at `components/data/ColumnPicker/`.

- **Live-apply, no confirm/cancel.** Toggling a checkbox immediately shows/hides that column on the `Table` — there is no pending/draft state and no "Đồng ý"/"Từ chối" step anymore (the 2026-08-17 first draft of this component had a toolbar-level confirm/cancel pair; that's retired). Closing the panel — via clicking the trigger again or clicking anywhere outside the panel — never discards anything, because nothing is ever "pending"; there's nothing to discard.
- **Unchecking a column hides its header cell AND every body cell — both, always together.** "Hide the column" means the `<th>` in the `Table` header and every `<td>` in that column across every row disappear as one unit; never hide just the cells while leaving a header with nothing under it, and never hide just the header while the cells still render (that reads as a broken/misaligned table, not a hidden column). The reliable way to get this for free: give the header cell and every body cell of a column the same `data-col="{key}"` marker and toggle one shared hidden-class (`.col-hidden{display:none}`) via a single selector (`[data-col="{key}"]`) — one toggle call reaches both without tracking header and body separately. Reference implementation: `mapApplyColumnVisibility`/`mapToggleColumn` in Mapping NVTT's own picker.
- **Trigger state**: clicking the settings icon toggles the panel and switches the icon to an **active/pressed** treatment (tinted `--color-bg-hover` background, `--color-border-focus` border, brand-colored icon) while open — this part is unchanged from the original spec.
- **Panel surface**: matches `Dropdown`'s own spec — white bg, `8px` radius, `1px solid --color-neutral-200`, `box-shadow: 0 8px 24px rgba(75,99,226,.12)`.
- **Positioning: `position: fixed` with JS-computed coordinates, not `position: absolute` anchored to the trigger.** `ToolbarSimple`'s own trailing cluster needs `overflow-x: auto` on narrow viewports (see that component's file) — an `absolute` panel nested inside that row gets silently clipped at the row's bottom edge instead of overlaying the `Table` below it, which is the whole point of a dropdown. Compute `top`/`left` from the trigger's `getBoundingClientRect()` at open time (`top = rect.bottom + 6`, `left = rect.right - panelWidth`) and give the panel a z-index above the `Table`'s sticky header/pinned columns (`z-index: 150` in the reference implementation, comfortably clear of `Table`'s own `z-index: 5–6`). Same technique `Table`'s own row-action `more_vert` menu already uses to escape `.table-inner`'s `overflow: auto` — don't reach for `position: absolute` here even though it looks simpler, it will clip.
- **Fixed anatomy, top to bottom (updated 2026-08-17 — reordered, search now comes before "Chọn tất cả")**:
  1. **Search row — conditional, not always present.** Only rendered when the column list has **more than 10 items**; at 10 or fewer, skip it entirely (the panel goes straight to "Chọn tất cả" — see the 8-column reference screenshot, which correctly has no search row). When shown: leading search icon, `placeholder="Nhập"`, no trailing chevron (a plain search field, not a `Select`-style combo). Typing filters the checklist below by label (case/diacritic-insensitive substring match); it never filters "Chọn tất cả" itself, which stays pinned below the search row regardless of the filter text.
  2. **"Chọn tất cả" (select all) row** — same 18px `Checkbox` visual as every other row here, but bold label. Checked when every column is currently visible; shows the **indeterminate** dash state (not the checkmark) when some-but-not-all are visible — same indeterminate convention as `Table`'s `rowSelection` header checkbox (see `references/components/data/table.md`). Toggling it shows/hides every column at once.
  3. **Checklist** — scrollable when long (`max-height` capped, 280–320px), one row per `Table` column, same 18px `Checkbox` visual + label. Every toggle here calls straight through to the `Table`'s actual column visibility — see live-apply note above. When `onReorder` is passed (see "Reordering columns" below), each row also gets a `drag_indicator`-style handle to its right, after the label — the checkbox/label part of the row is unchanged either way.
- **Gap handling**: this trigger is declared as icon-only with no label anywhere else in the DS (`ToolbarSimple`/`FilterCard`'s closed action tables) — don't add a text label to the gear button to "make room" for this panel; the active-state recolor is the only visual change the trigger itself gets.

## Every option must render a real column — no decorative/no-op checkboxes (added 2026-08-26)

`options` is documented on `ColumnPickerProps` as "every column the Table can show" — that's a hard requirement, not aspirational phrasing. Checking a box in the checklist must make that column actually appear in the `Table` with real cell content on every row. A checkbox that toggles with no visible effect on the table is a bug in the screen, not an acceptable scoping shortcut — it reads to the user as broken, not as "not built yet."

- **If a field genuinely has no value for some rows** (a real domain field that's just empty on that particular record) — render the `Table`'s existing empty-cell convention (`—`, `--color-text-muted`, `references/components/data/table.md`). That's a legitimate "no data on this row" state, not what this rule targets.
- **If a field has no data source wired up at all** (a name pulled from a spec/catalog/uploaded field list that was never connected to the mock or real dataset) — when it's added as a `ColumnPicker` option, Claude must synthesize plausible sample values for it on every row the moment it's checked, not leave the column blank and the checkbox inert. Generate values that fit the field's evident type (a date field gets a date, a status/enum field gets one of that field's real option values, a free-text field gets a short realistic string) — the same effort already going into populating the rest of the mock dataset, not a single repeated placeholder token like "N/A" copy-pasted down the column.
- **Don't ship a `ColumnPicker` option that has no effect when checked.** If a field is only there for "catalog completeness" and isn't meant to be viewable yet, leave it out of `options` entirely rather than wiring up an inert checkbox — ask the user instead of silently defaulting either way: *"Trường X chưa có dữ liệu nào cả — Claude tạo dữ liệu mẫu để hiện cột này, hay bỏ khỏi Cài đặt bảng cho tới khi có dữ liệu thật?"*
- **Retrofit on sight.** An already-shipped `ColumnPicker` with inert catalog-only options is a violation of this rule the moment it's noticed, not a grandfathered exception — fix it in the same turn (either populate sample data or remove the option), the same "don't leave it stale" standard the Propagation rule (`references/component-rules.md`) already applies to component markup changes.

## Reordering columns (`onReorder` prop, added 2026-08-26)

Show/hide is the only control the checklist has by default. Pass `onReorder` to also let a row be dragged to a new position — this is opt-in, not a behavior change for existing pickers that don't pass it.

- **Handle, not the whole row — always visible on the right, drag/hover affordance modeled on Ant Design's own drag-list pattern (revised 2026-08-26; revised again same day — a hover-reveal draft of the handle itself was tried and reverted, see below).** A `drag_indicator`-style handle (two columns of 3 dots) sits to the **right** of each checklist row, after the label (revised 2026-08-26 — the first draft of this rule placed it on the left; the trailing position reads more like an accessory action and less like it's part of the click target for the checkbox/label).
  1. **The handle is always visible**, not hover-revealed — a same-day draft made it fade in only on row hover (`opacity:0` at rest), matching Ant Design's own reference more literally, but that was explicitly rejected: the handle must stay always-on.
  2. **Row hover** tints the row `--color-bg-hover`, same as any other hoverable row.
  3. **Handle hover** switches the cursor to `grab` — the row's own cursor stays default, signaling the handle (not the row's label/checkbox) is the intended drag origin, even though the whole row is the underlying native-drag source.
  - Drag the handle, not the row's label text or its checkbox — the checkbox stays a normal click target for show/hide, it doesn't also start a drag.
- **Drop-position indicator: an `inset` `box-shadow` line on the hovered row itself — not a separate element (settled 2026-08-27 after two failed drafts).** While dragging, the row currently under the pointer keeps its hover tint and gets a thin `--color-border-focus` line along its **top** edge, via `boxShadow: 'inset 0 2px 0 0 var(--color-border-focus)'` applied directly to the row's own style/class. Insertion is always immediately above the hovered row (matches the actual insert-before-target mechanics — hence the line sits at the *top* edge, not the bottom); the row being dragged never shows the line on itself.
  - **Why a `box-shadow` on the row, not a separate slot element — two earlier drafts each had a real bug:**
    1. **In-flow sibling** (first draft): inserting a real block element directly after the hovered row pushes every later row down. This isn't just a style nitpick — it shifts every later row's `offsetTop` *mid-drag*, and the browser re-hit-tests `dragover` against the pointer's *screen position* on every such layout change, so the row that was under the pointer gets shifted out from under it. This broke dragging a column **downward** past several rows: the drag would jitter or get stuck instead of reaching the intended target.
    2. **Absolutely-positioned overlay** (second draft, direct fix attempt for #1): rendering one `position: absolute` slot block (sized like a full row) at the checklist-container level, positioned via the hovered row's `offsetTop`/`offsetHeight`, does stop the jitter — nothing's `offsetTop` changes anymore. But since no row moves to make room for it either, the overlay now sits **on top of** whatever row comes next, visually covering that row's checkbox and label text.
    3. **`box-shadow` (final, correct)**: never affects layout at all — it's not a real element, isn't inserted or moved, and is drawn `inset` (inside the row's own border box, in the row's existing padding, clear of the label/checkbox content) rather than needing any space of its own. This is the only option that is simultaneously immune to #1 (nothing's `offsetTop` ever changes — it's not even a new box) and #2 (nothing is layered over adjacent content — it's confined inside the hovered row's own box). Toggle the shadow (or an equivalent class) on/off directly on the row/anchor-item element itself; don't reach for a separate slot node again.
  - Reference implementation: `ColumnPicker.jsx`'s `ReorderableRow` conditional `boxShadow` inline style, mirrored in Mapping NVTT's own picker via the shared `.cp-drag-over` class (`mapCpDragOver`/`mapGroupDragOver` toggle it directly on `.cp-row`/`.cp-anchor-item`).
  - **Square off the top corners while the line shows (revised 2026-08-27).** An inset `boxShadow` still conforms to the row's own `border-radius` — with the default rounded corners left in place, the line curves into an arc at each end, reading as a short border segment rather than a clean straight line spanning the full row width. Override `border-radius` to `0 0 6px 6px` (top corners squared, bottom stays rounded) only while `dragOver` is true for that row — this is what actually makes it read as a *line*, not a border.
- **Live-apply, same as visibility.** Dropping a dragged row onto another fires `onReorder` immediately with the full next `options` array (resequenced, and with the dragged item's `group` updated if it moved sections — see below) — no separate "Save order" step, no pending state. Same reasoning as the show/hide toggles: nothing here is ever a draft.
- **Flat variant**: a dragged column can be dropped anywhere in the one list — first, last, anywhere between.
- **Grouped variant: dragging can move a column into a different group (revised 2026-08-26 — reverses the original same-group-only draft of this rule).** Dropping a dragged row onto a row that belongs to a *different* group's section moves the column into that group: its `options[i].group` is reassigned to the target section's group, and it's inserted at the drop target's position within that section. Dropping onto a row in its own group just reorders within that section, same mechanics as the flat variant — there's exactly one drop behavior, "insert at the target row's position, adopting the target's group," and same-group vs. cross-group are just two cases of it, not two different code paths to keep in sync.
- **Disabled while the search filter has text in it.** A filtered checklist shows a subset of the real order — dragging within that subset has no unambiguous "where does this land in the full list" answer, so the drag handle simply doesn't render until the search box is cleared. Don't try to compute a best-guess destination; require the unfiltered view instead.
- The drop-position indicator line (above) applies identically in both flat and grouped variants, including when hovering a row in a different group — the line still shows, signaling "drops here, reassigned to this group."
- **`options` order (and group assignment) is the caller's responsibility, not the picker's own state.** `ColumnPicker` never mutates `options` itself — it only reports the full next array via `onReorder`. The caller applies that array back onto both its own `options` state (so the picker's next open reflects it) and the `Table`'s actual column order/grouping; a drag that updates the picker's own list but not the `Table` underneath it is the same class of bug as a checkbox that toggles with no effect on the `Table` (see "Every option must render a real column" above) — the picker's UI state and the `Table`'s real state must never drift apart.
- **Applying the `onReorder` array: only rebuild the column list — never reset visibility, never re-derive group assignment (added 2026-08-27, from a real regression in Mapping NVTT's own picker).** The `next` array `onReorder` fires with is already fully correct — right order, and the dragged item's `group` already updated if it moved sections. The caller's handler has exactly one job: store that array as the new `options`. Two things it must NOT also do as a side effect:
  - **Must not reset which columns are checked/visible.** A drag reorders or regroups a column; it never changes which columns are shown. The regression this guards against: Mapping NVTT's `mapCpDrop` handler called a broader `mapRecomputeColumnPickerState()` after every successful drag — that function correctly rebuilt the column list, but it *also* rebuilt the visible-columns set from scratch (every non-"extra" column back to checked, every "extra" column back to unchecked), silently re-checking any column the user had manually unchecked, on every single drag. Fix: only rebuild the list itself (`mapToggleableCols = mapComputeToggleableCols()` — no separate step that touches the visible-keys set).
  - **Must not re-derive a moved column's group from some other/stale source.** If the caller recomputes its column list by re-reading a source of truth that hasn't itself been updated to reflect the drag, a cross-group move can silently revert (the column snaps back to its original group instead of staying in the one it was dropped into). Apply the `next` array's `group` values as-is — don't recompute group membership from elsewhere.

## Reordering groups (`onGroupsReorder` prop, added 2026-08-27)

Grouped variant only (see "Variant: flat vs. grouped-with-anchor" below) — a separate, independent opt-in from `onReorder`. `onReorder` reorders/regroups *columns within* the anchor's sections; `onGroupsReorder` reorders the *sections themselves* — which group's block comes first, second, third in both the anchor nav and the checklist. A caller can offer either, both, or neither.

- **Originates from a real screen need**: Mapping NVTT's "Cài đặt hiển thị" picker groups columns into Pháp luật / Nội bộ / Căn cứ xử phạt, and the request was specifically to let the user swap the position of two of those groups (e.g., viewing "NVTT Pháp luật," swap "Nội bộ" and "Căn cứ xử phạt") — this generalizes that into the reusable component instead of leaving it as one-off vanilla-JS-only behavior.
- **Same drag/drop-over visual language as `onReorder`'s checklist rows — not a separate design.** Each anchor entry gets the identical treatment: an always-visible `drag_indicator`-style handle, a `--color-border-focus` line via `boxShadow` (not a separate slot element — the same reflow-jitter and text-covering bugs documented in "Reordering columns" above apply equally here, since it's the same kind of list), squared top corners while the line shows, and the dragged entry itself dimmed to `opacity: .4`. Two different-looking drag interactions in one panel would read as two unrelated features; keeping them visually identical signals "this is the same kind of gesture, just at a different level" — which is exactly what it is.
- **No same-group-only restriction, and no built-in locked/pinned entry.** Every group in `groups` can be dropped onto every other — there is no concept of a "current" or non-draggable group inside `ColumnPicker` itself. A screen that needs one group pinned (e.g. tied to an active tab elsewhere on the page, the way Mapping NVTT's anchor group tracks its own "Xem theo" tab) implements that itself at the call-site — `ColumnPicker` doesn't know about tabs or views, only about the `groups` array it's handed.
- **Live-apply, no confirm step** — same reasoning as every other control in this panel: dropping fires `onGroupsReorder` immediately with the full next `groups` array, no pending state.
- **Applying the array follows the exact same rule as `onReorder`'s array** (see above): only store it as the next `groups` — don't let the handler also reset unrelated state as a side effect.
- **Handles must align in a straight column, not follow each label's own width — give the label `flex:1; min-width:0` plus ellipsis truncation, not bare unconstrained text (a real bug, fixed 2026-08-27).** The anchor nav is a fixed-width column (`130px`); a label wrapped in `white-space: nowrap` with no `min-width:0`/overflow handling can grow its own row wider than its siblings when the label text is long (e.g. "Căn cứ xử phạt" vs. "Nội bộ") — since `justify-content: space-between` positions the handle at *that row's own* right edge, a wider row's handle ends up visibly offset from the handles on narrower rows, breaking the straight vertical line handles are supposed to form down the anchor column. Wrap the label in its own element with `flex: 1; min-width: 0; overflow: hidden; text-overflow: ellipsis; white-space: nowrap` (`ColumnPicker.jsx`'s `AnchorItem` label `<span>`) so a too-long label truncates instead of widening the row — this is what actually keeps every handle at the same x-position regardless of label length.

## Variant: flat (default) vs. grouped-with-anchor

`ColumnPicker` has two layouts. **Flat is the default and the one to reach for unless told otherwise** — everything in the anatomy section above. Pass the optional `groups` prop (an array of `{key, label}`, with each `option` carrying a matching `option.group`) to switch to the **grouped variant** instead: a left anchor nav (one entry per group) next to a wider list where the checklist is broken into labeled sections, one per group, in `groups` order.

- **Grouped anatomy**: panel widens from `260px` to `460px`. Left column (`130px`, right border) lists the group labels as click targets — clicking one scrolls the list to that group's section. The search row / "Chọn tất cả" row / checklist from the flat anatomy all move into the remaining right column (search and "Chọn tất cả" sit **above** the list, to the right of the anchor — not spanning above it) — the anchor column has nothing in it but the group labels, full height.
  - **Scroll-spy, not just click-to-scroll**: the anchor doesn't only highlight on click — scrolling the checklist by any means (mouse wheel, trackpad, dragging the scrollbar) continuously re-evaluates which group's section is at the top of the visible list and highlights that group's anchor entry. Reference implementation: `mapCpUpdateActiveAnchor`/`mapCpScrollTo` in `can-cu-xu-phat-ias-redesign 6.html` (Mapping NVTT's own picker), mirrored in `ColumnPicker.jsx`'s `handleListScroll`/`scrollToGroup`.
  - Section header text is the group's own `label`, uppercase, `11px/700`, `--color-text-muted` — same visual language as `DrSectionTitle`'s title row scaled down, but without the accent bar (this is a plain list divider, not a full section-title component).
  - "Chọn tất cả" and the live-apply/no-confirm behavior are unchanged — they still act on the full flattened option set across every group, not per-group.

### Variant selection — the rule to actually follow when building a new ColumnPicker
This is a judgment call every time a new picker gets built, not a one-off decision baked into the component. Apply it fresh per screen:

1. **Under ~20 options total: always flat**, regardless of whether the fields conceptually belong to different domains/groups. An anchor nav is overhead a short list doesn't need — the existing search threshold (>10 items) is already enough of an aid at that size.
2. **Past ~20 options, the grouping question becomes real** — this is where the two variants start to matter:
   - **Default to flat + search.** If the user hasn't said anything about grouping the fields — no mention of categories, domains, or "chia nhóm" — don't invent groups on your own initiative just because the option count crossed 20. Flat-with-search is the safe default; it always works even when the underlying options don't have a natural grouping.
   - **Use the grouped variant only when the user has explicitly indicated the options should be grouped** — they name the groups, describe the fields as belonging to distinct categories, or ask directly for a grouped/anchored picker (e.g. Mapping NVTT's "Cài đặt hiển thị" — Pháp luật / Nội bộ / Căn cứ xử phạt, requested by name). Don't infer a grouping from field-name patterns on your own; wait for the user to say so.
3. **When genuinely ambiguous** (the user gestures at "a lot of fields" without saying whether they're grouped) — default to flat per rule 2, and ask only if the option count is large enough (well past 20) that the choice will visibly matter once built.
