# Table
- Header row: `--color-bg-page` background, **uppercase** 11px bold text with letter-spacing (the one place uppercase is correct — see cross-cutting rule).
- **Full grid borders on `td` only, `th` borderless (updated 2026-08-18):** every `td` gets `border:0.5px solid var(--color-border-default)` on all 4 sides (`border-collapse:collapse` on `<table>` merges the shared edges into single lines) — not the older bottom-only row divider, and thinner than a standard 1px rule. `th` (the header row) has **no border at all** (`border:none`) — the header/body divider line comes from the first body row's `td` top border, not from `th`. This gives the table left/right borders between and around every body column, in addition to the horizontal row separators, while keeping the header visually border-free. Drop any `tbody tr:last-child td{border-bottom:none}` exception; the last row keeps its bottom border so the grid is complete.
- **No border-radius, no wrap border (updated 2026-08-18):** `Table`'s own wrapping element (`.wrap`/`.table-wrap`) is square-cornered (`border-radius:0`, not the 12px the generic Card rule uses elsewhere) **and has no border of its own** (`border:none`) — the table's edge is defined purely by the `td` grid lines, not an outer frame. This applies even when that wrapper is inset (padded, not flush) inside an outer rounded/bordered card or list-panel — the table itself still renders with sharp, borderless corners; only the outer card around it (if any) keeps its own 12px radius + border.
- Row identity: avatar (28px) + name combined in a single first column — never a separate "avatar" column next to a separate "name" column.
- Status cells always use the dot+pill Badge-style treatment (cross-cutting rule), never a plain colored word.
- Row-level actions are **one of three** options — a text link ("Xem ›"), an icon `more_vert` overflow trigger, or an icon `keyboard_double_arrow_right` trigger that opens a `Drawer` with the row's full detail. Pick text-link for one dominant navigate-away action, `more_vert` for several menu actions, `keyboard_double_arrow_right` when the primary action is viewing full detail inline without leaving the list (see `references/components/overlay/drawer.md`). When `more_vert` is the pick, the menu it opens is **`RowMenu`** (`references/components/data/rowmenu.md`) — text-only items (no icons), auto-sorted into the canonical order (Xem chi tiết → Chỉnh sửa → Gửi duyệt → Lịch sử thay đổi → Xóa) — not a bare `Dropdown`/`DropdownMenuItem` with icons.
  - **Exception (added 2026-08-17):** `keyboard_double_arrow_right` and `more_vert` may coexist in the same table when they serve genuinely non-overlapping purposes — the arrow opens the `Drawer` (quick view, no navigation away), `more_vert` holds everything else (e.g. "Lịch sử thay đổi", "Xóa") with no duplicate "view detail" entry inside it. This is still a **closed pair**, not a free-for-all: never combine `keyboard_double_arrow_right` with a text-link, and never let `more_vert` re-offer the same "view detail" action the arrow already provides (that's the redundant-duplicate case the original "never more than one" wording was guarding against). `can-cu-xu-phat-ias-redesign.html` is the reference example — its `more_vert` menu dropped its own "Xem chi tiết" entry once the arrow trigger was added to the Mã phạt column.
  - Text-link and `more_vert` stay in the **last column**, as before.
  - `keyboard_double_arrow_right` is the one exception — it does **not** go in a trailing action column. Updated 2026-07-31 (corrected from an earlier last-column version of this rule): place it as its own narrow, unlabeled column **immediately after the row's primary identifying (mã/code) column** — near the front of the row, not the end. This matters because these tables are frequently very wide (many columns, horizontal scroll) — a trailing trigger would be scrolled out of view, while the identifying column is always the one users look at first.
  - **Auto-placement heuristic** when converting an upload: scan the row's columns left-to-right for the first one that is (a) a dedicated `mã`/code field (e.g. "Mã văn bản", "Mã chương trình"), or (b) a combined code+content column (e.g. "Thủ tục" rendering `{{Mã TT}}-{{Nội dung}}`) — insert the trigger's column immediately after that one. If several `mã`-type columns exist, anchor to the first/primary one that identifies the row (usually right after any leading checkbox/STT column), not a secondary code column further right (e.g. a linked/foreign-key mã appearing mid-table).
- A `FilterCard` sits directly above the `Table` it filters, with the DS's standard content-gap spacing between them (16-20px) — never nested inside the table's own card surface.
- **Row selection (`rowSelection` prop, added 2026-07-23)**: a leading checkbox column, always the first column (before row identity) — never appended at the end. Header checkbox is select-all, showing the indeterminate (dash) glyph when some-but-not-all rows are checked. Reuses the same 18px checkbox visual as `components/forms/Checkbox` (brand-fill square + white check/dash) — don't invent a different check style for the header vs. body checkboxes. Clicking a row checkbox must not also fire `onRowClick` (stop propagation). Pair with `ToolbarSimple`'s bulk-selection bar (see that component's section) to surface the "Đã chọn N" summary + bulk actions — a table with `rowSelection` but no visible selection feedback in the toolbar above it is an incomplete pairing, not a valid end state.
